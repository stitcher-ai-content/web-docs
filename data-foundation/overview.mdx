Everything StitcherAI does starts with getting data in and ends with sending curated output back out. Both directions are built from the same three concepts, and once you know them you can read every connection in your model.

## Three concepts that combine

<CardGroup cols={3}>
  <Card title="Dataset" icon="table">
    *What* the data is and what it means — an AWS cost & usage export, an OpenAI usage dataset, a vendor invoice, a business-data file.
  </Card>
  <Card title="Connector" icon="plug">
    *How* StitcherAI reaches the data. Three families: file / blob storage, database, and provider API.
  </Card>
  <Card title="Data connector" icon="arrow-right-arrow-left">
    A dataset **+** a connector, set up as a **data source** (data in) or a **destination** (curated output out).
  </Card>
</CardGroup>

So a "data connector" is always a dataset paired with a connector, pointed either inward as a source or outward as a destination. That one pattern covers everything you connect.

## Kinds of dataset

<AccordionGroup>
  <Accordion title="Cost datasets" icon="file-invoice-dollar">
    Spend itself — cloud, SaaS, AI, vendor invoices, and internal IT. These are normalized to [FOCUS](/data-foundation/focus), the open cost language.
  </Accordion>
  <Accordion title="Business datasets" icon="sitemap">
    The context that makes spend meaningful — ownership, teams, cost centers, headcount, revenue, budgets. You use them later to enrich cost, drive allocation, and measure KPIs.
  </Accordion>
  <Accordion title="Reference / feature data" icon="chart-line">
    Business series such as headcount or customer count over time. Brought in to improve forecasts beyond historical cost alone.
  </Accordion>
</AccordionGroup>

Most data is **structured** — Parquet, CSV, or database tables. StitcherAI also ingests **unstructured** data, principally **PDF** invoices, which it maps into the cost model with AI. See [AI-powered ingestion](/data-foundation/ai-ingestion).

## A shared, multi-purpose source connection

You don't re-enter connection details every time you add a source. A **shared, multi-purpose source connection** holds only the reusable parts of an integration — the credentials and the location of a system — with no dataset attached. You define it once in the web app, then craft as many data sources from it as you need in the StitcherAI Editor, declaring each one **cost** or **business** at the point of use.

<Steps>
  <Step title="Define the shared connection once">
    Enter the location and credentials for a system — a storage bucket or account, a warehouse — in the web app. No dataset is attached; StitcherAI validates the credentials and location. See [Connections & credentials](/data-foundation/connections-and-credentials).
  </Step>
  <Step title="Craft a source from it">
    In the editor, add a data source and pick the shared connection from its own group in the source picker. You add only what is specific to this source — the folder or table, and its options.
  </Step>
  <Step title="Declare it cost or business">
    A **cost** source is spend that StitcherAI normalizes to FOCUS. A **business** source is context — ownership, teams, budgets — joined to cost later. The shared connection is the same either way.
  </Step>
  <Step title="For a cost source, choose the provider">
    A cost source also names its **provider** and its schema — FOCUS or custom — so StitcherAI knows how to normalize it. A business source needs neither.
  </Step>
</Steps>

**One connection, many purposes.** The same shared connection to a storage account can back an AWS cost export in one folder and a headcount file in another; the same warehouse connection can back Snowflake usage and a cost-center table. Shared connections are for sources — a destination is always a dedicated connection with its dataset attached.

<Tip>
Credentials never live in your configuration repository — only the connection's *name* is referenced from the model. The full reasoning, and how validation works, is in [Connections & credentials](/data-foundation/connections-and-credentials).
</Tip>

## What you can connect

StitcherAI is best understood by **retrieval family** rather than a connector-by-connector list. The table shows the breadth — which providers are covered, an example dataset for each, and how the data is retrieved. The named catalog, with what each provider ingests and how you set up access, is on [Supported integrations](/data-foundation/integrations).

| Provider(s) | Example dataset | How it's retrieved |
|---|---|---|
| AWS | Cost & Usage (CUR, CUR 2.0), FOCUS export | File / blob storage (S3) |
| Azure | FOCUS export, MCA billing export | File / blob storage (Azure Storage) |
| Google Cloud | Billing export, FOCUS billing export | Database (BigQuery) or blob (GCS) |
| Snowflake | Organization usage & cost | Database |
| Databricks | Usage report | Database |
| OpenAI · Anthropic / Claude · Twilio · MongoDB Atlas · Elastic Cloud · Confluent Cloud | Usage & cost | Provider API |
| Any vendor | Invoice / custom cost (including PDF) | File / blob storage |
| Internal teams | Business data (ownership, headcount, budgets) | File / blob storage, database, or in-repo |

<Note>
New providers are added without changing the model — a source is always a dataset plus a connector in one of the three families above. For arbitrary vendors (cloud, SaaS, or non-IT) and for PDFs, see [AI-powered ingestion](/data-foundation/ai-ingestion).
</Note>
