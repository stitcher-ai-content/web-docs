A run executes your cost model end to end: it connects to your sources, normalizes and attributes the data, builds artifacts, evaluates governance, and delivers output. This page covers the three ways to run it, how to watch a run, how to read a failure, and the pipeline settings that govern production runs — [automatic retry and notifications](/retry-and-notifications) and [execution rules](/execution-rules).

<Note>
Looking for the hands-on version instead? [How to: Execute a pipeline](/how-to/execute-a-pipeline) walks through running a pipeline, watching it, and fixing a failure.
</Note>

## The three run types

They differ only in **scope**, **where output goes**, and **whether governance and notifications fire**.

<CardGroup cols={3}>
  <Card title="Standard run" icon="play">
    The full model — all stages, all sources, whole-month periods. Governance and notifications fire; output goes to **all** destinations.
  </Card>
  <Card title="Scheduled run" icon="clock">
    A hands-off standard run on a schedule you define (for example, daily). Normal production.
  </Card>
  <Card title="Debug run" icon="flask">
    A scoped, low-cost run to validate a change. Writes to a **debug** destination; notifications suppressed.
  </Card>
</CardGroup>

<Tabs>
  <Tab title="Standard run">
    The full model: all stages, all configured sources, and whole-month periods (the current month can be month-to-date). Governance is evaluated, notifications fire, and output is written to every configured [destination](/engage/engage). Use it to **backfill or update** data — and note that a schedule invokes exactly this kind of run.

    <Warning>
      A standard run updates the production data your organization relies on. Run it deliberately — for routine production, prefer a scheduled run.
    </Warning>
  </Tab>
  <Tab title="Scheduled run">
    A standard run on a schedule you define — daily, weekly, or monthly at a time you choose — left to run unattended. This is normal production operation. It runs the full scope at each interval and takes no extra inputs; a scheduled run can't be named or put into debug mode, because the point is that it runs the same full model every time without anyone starting it.

    Because it runs unattended, scheduled runs are where [automatic retry](/retry-and-notifications#automatic-retry) matters most: when a provider's export hasn't landed yet, the run waits and tries again rather than failing for the day.
  </Tab>
  <Tab title="Debug run">
    A scoped, low-cost run for validating a change **before it ships**. You narrow it three ways and run it against the branch you're working on (see [Authoring & version control](/authoring/version-control)):

    <Steps>
      <Step title="Limit the period to a single day">
        Pick one day within a month rather than the whole month, so the run is cheap and fast.
      </Step>
      <Step title="Narrow the data scope">
        Run one provider, or a single data source within a provider. Business data still processes, because downstream steps depend on it.
      </Step>
      <Step title="Run only the stages you're changing">
        Pick a **start stage** and an **end stage**. A new debug session always starts at Connect; a follow-up run can start at any stage the previous session completed, plus the next one. Model's sub-stages — **Prepare, Normalize, Enrich, Allocate** — are each valid start and end points, so you can resume at Enrich without re-running Normalize. Start *at* the stage you're editing so your change actually executes.
      </Step>
    </Steps>

    A debug run writes to a **debug destination** rather than production, and **notifications are suppressed** — so you can iterate freely without touching live data or alerting anyone. Debug runs can be named, but can't be scheduled.
  </Tab>
</Tabs>

## Watching a run

Open a run on the **run details page** to watch it live.

<Frame caption="The run details page: per-stage progress and failure logs">
  ![The run details page: per-stage progress and failure logs](/images/fig-16-run-details.png)
</Frame>

The page shows **per-stage and per-step progress**: which stage is running, which steps have completed, and which is in flight. (For what each stage does, see [How a pipeline is composed](/pipeline-overview).)

<Note>
A pipeline runs **one run at a time**. Runs can be **named** — so a backfill is easy to find later — and **cancelled** from the run details page if you need to stop one. A run that is waiting for an automatic retry counts as in progress: the pipeline waits until the retry completes or you cancel it.
</Note>

### Run statuses

Alongside running, completed, failed, and cancelled, two statuses come from [automatic retry](/retry-and-notifications#automatic-retry):

| Status | What it means | What happens next |
|---|---|---|
| **Retry scheduled** | The run stopped because expected data wasn't available yet, and a retry is booked for a later time. Not final. | StitcherAI starts the retry automatically at the scheduled time. Cancel the run to free the pipeline instead. |
| **Precondition failed** | Expected data wasn't available and no retries remain (or retry is off). Final. | Read the [precondition-failure report](#the-precondition-failure-report), fix or wait for the data, then run again. |

A retried run keeps the original's name and schedule and records which run it retried and the attempt number, so the sequence reads cleanly in the run list.

### Sources marked Skipped

A source can show as **Skipped** in the run graph for two reasons: it had no data for the period (the run still succeeds), or an [execution rule](/execution-rules) told the run to skip it. The rules applied to a run are recorded on the run itself, so you can tell which. A distinct label for rule-driven skips is coming.

## Diagnosing a failure

When a step fails, the run details page is also where you fix it.

<Steps>
  <Step title="Open the failed step">
    The failed step is marked, with its **error and logs** shown directly. Read the reason there — you don't go hunting for it. If the failure is a missing-data precondition, you'll see a table instead of a raw error (below).
  </Step>
  <Step title="Fix the configuration">
    Make the change in the [StitcherAI Editor](/authoring/version-control) on your working branch.
  </Step>
  <Step title="Re-run a scoped debug run">
    Re-run on just the relevant scope — the single day, the one source, the stages you changed — to confirm the fix cheaply.
  </Step>
  <Step title="Promote when it's clean">
    Once the debug run passes, merge your change and let a standard run (or the schedule) update production.
  </Step>
</Steps>

<Tip>
A recent debug session keeps the work already done, so a follow-up debug run can **start from a stage you've already passed** instead of re-running everything. Restart points go down to Model's sub-stages — Prepare, Normalize, Enrich, Allocate — so iterate on exactly the stage you're changing.
</Tip>

### The precondition-failure report

Some checks run before a source is processed — for example, that a business dataset has data for **every day in the period**. When a configured precondition fails, the run graph shows a **precondition table** so the failure tells you where and why:

| Column | What it shows |
|---|---|
| **Precondition** | The kind of check — data exists, daily coverage, and so on |
| **Name** | The source or dataset it was checked against |
| **Status** | **Pass** · **Failed — data** (the data is missing) · **Failed — configuration** (the check itself is misconfigured) |
| **Reason** | The reported reason; expand the row to see the **missing dates** |

A precondition failure stops the run deliberately, before it produces partial output. It's also the one failure type [automatic retry](/retry-and-notifications#automatic-retry) can recover from — if retry is on, the run shows **Retry scheduled** rather than **Precondition failed** until attempts run out.

## Governing production runs

Three pipeline-level settings shape how production runs behave. None of them require editing the cost model.

<CardGroup cols={3}>
  <Card title="Automatic retry" icon="rotate-right" href="/retry-and-notifications#automatic-retry">
    Off by default. When expected data isn't available yet, wait an interval and try again — up to a set number of attempts.
  </Card>
  <Card title="Run notifications" icon="bell" href="/retry-and-notifications#run-notifications">
    Choose the run events, the notification groups (email, Slack, webhook), and the run types that notify. Toggle off per run.
  </Card>
  <Card title="Execution rules" icon="filter" href="/execution-rules">
    Skip a provider or a source over a bounded window so the schedule keeps producing everything else. Outputs are partial for that window.
  </Card>
</CardGroup>
