## What this does, and why

**Attribution** assigns cost to a clear owner — a team, product, or cost center — so every relevant organizational construct, shared ones included, has a clear view of its own cost. It's distinct from **allocation**, which takes cost already attributed to a shared service and distributes it onward, across a set of receivers, based on an allocation strategy. See [Enrich](/pipeline/model/enrich) for the full concepts.

Attribution mostly happens during **[Enrich](/pipeline/model/enrich)**, the third Model sub-stage, once your data is already normalized to FOCUS. It uses two operators:

<CardGroup cols={2}>
  <Card title="Mapping" icon="list-check">
    Derives an owner from rules on the values already present in the cost data — for example a naming pattern.
  </Card>

  <Card title="Lookup" icon="link">
    Joins an ownership table onto each cost row by matching a key — the standard way to attach ownership from a business dataset.
  </Card>
</CardGroup>

<Note>
  This assumes you already have a connected, FOCUS-normalized dataset. If you haven't brought one in yet, see [How to: Bring in a dataset](/getting-started/bring-in-a-dataset) first.
</Note>

## Choose Mapping or Lookup

<Steps>
  <Step title="Use Mapping when the owner is derivable from rules">
    If ownership can be worked out from values already in the cost data — an account-name prefix, a tag pattern, a threshold — add a **Mapping**: an ordered set of conditions that derive or update a column, with a default value for rows that match none. Example: derive `x_team` or `x_cost_center` from an ordered set of naming-pattern rules.
  </Step>

  <Step title="Use Lookup when ownership lives in a separate dataset">
    If ownership lives in a business dataset — an ownership spreadsheet, a headcount export — add a **Lookup**: it merges columns from that business dataset into the cost dataset by matching values in a join column, letting you rename imported columns and choose how duplicate matches are handled. Example: attribute resources to owners via a mapping table.
  </Step>

  <Step title="Combine them where needed">
    Enrich runs its configurations in order, so a Lookup that attaches a raw owner id can feed a later Mapping that derives a friendlier team name from it — or the reverse. Order the configurations so each step has the columns it depends on. See [order is honored where it matters](/pipeline/overview#how-a-pipeline-is-composed).
  </Step>
</Steps>

Both operators — like every Enrich operator — share the same building blocks: **scope** to limit which providers or sources a rule touches, **conditions** to test column values, and **merge behavior** (add, update-if-empty, or overwrite) to control how the result is written. See [the shared building blocks](/pipeline/overview#building-blocks-shared-across-stages).

## Worked example — Mapping by account name, Lookup by ownership table

- **Mapping (rules already in the data):** AWS cost rows arrive with an `AccountName` column, for example `AccountName = "prod-search-us-east"`. A Mapping derives `x_team` from it: `AccountName` starting with `prod-search` sets `x_team = "Search"`; starting with `prod-checkout` sets `x_team = "Checkout"`; anything else defaults to `x_team = "Shared"`. No separate dataset is needed since the pattern is already in the column.
- **Lookup (ownership lives elsewhere):** Kubernetes namespace costs arrive with only `NamespaceId = "ns-4471"`, with nothing self-describing. A business dataset maps `NamespaceId` to `Team` (`ns-4471` maps to `Platform Engineering`). A Lookup joins on `NamespaceId` and pulls in `Team`, so those rows get `x_team = "Platform Engineering"` from the ownership table rather than a naming pattern.
- **Combining them:** A Lookup first attaches a raw id from a business dataset (`owner_id = "eng-042"`); a later Mapping translates that raw id into the friendly name used in reports (`eng-042` becomes `"Platform Engineering"`).

## Handling unmatched rows

<Tip>
  Both **Lookup** and **Mapping** support a **default value** for rows that match no rule — use it to catch unmatched rows and attribute them correctly, instead of letting them fall through as shared cost.
</Tip>

If no default is set and no rule matches, the row is left without an owner — set a default value on the Mapping or Lookup so every row gets attributed, even if only to a general owner like `Shared`.
